## Responses to challenges

### CHATGPT

#### CHATGPT-A — “Bounded extension” is premature

**Conceded in substance.** My proposal's “the remaining work is the differentiators, not the plumbing” framing was too optimistic. The verified routing runbook describes no per-turn policy hook, requires failure rather than fallback, and places model-mapping fixes at the adapter boundary (V5). The chats guide shows delegated work is another bot in its own chat and that restart stops work and `Try again` submits the task again as a new card (V3). A provider change starts a fresh provider session (V4). So a provider-neutral skill layer, per-task routing, safe external-write resume, parent/child accounting, shared pages, task ratings and a triage gate are interconnected runtime behaviour, not a sidecar policy file. I withdraw “bounded” as a load-bearing description.

The accurate statement is narrower: Akeru supplies substantial, already-written commodity surface — clients, named profiles, groups, provider connections, plugin/MCP lifecycle, memory files, still-image generation, a WhatsApp DM channel and a usage page — but it does not supply the differentiators, and the cost of adding them is unmeasured. A local bot profile is a structural starting point, not evidence that persona, memory, skills and task progress survive a real switch with uncertain tool effects.

#### CHATGPT-B — The Natalia → Rajiv test

**Accepted as the decision gate.** Your test is the right one, and I would add only the distinction the evidence now makes explicit: exactly-once *delegated-result delivery into the chat* is documented (V3), while exactly-once *external side effects* is not. A phone call, WhatsApp send or calendar write accepted before a restart is outside the result-delivery guarantee. The retry path starts new work for the same bot with the same task and a new card; the original card keeps its result. If the fix requires two authorities for retries, dispatch and accounting — the platform controller plus a new orchestrator/task store — option 4 can win even if patching Akeru is technically possible. I accept that threshold. If the fix is confined to an adapter plus a task ledger used by dispatch, option 3 stays first. I cannot pass the test from documentation; it remains unresolved.

#### CHATGPT-C — DEEPSEEK-1 overstates the shim case

**Conceded.** Provider independence is not identical to independence from the application that stores the bots. A stable vendor application could hold one bot identity while inference changes; my original “structurally impossible” wording was too strong. The narrower verified grounds for ranking option 1 third are enough, but they are narrower: Grok Bot is cloud-only and Cursor-managed, with no customer-facing model picker and usage recorded as Grok Bot usage rather than by model (V13); the shim documents only Codex OAuth, OpenAI-compatible chat completions and a canned stub, with no Claude, DeepSeek or Grok subscription route, an isolated profile, and no mention of connected apps (V14); and hosted connector tokens remain on Cursor's backend (as established in the assessment context and my challenge pass). Option 1 can be a migration bridge and a UI/connector reference; it is not the provider-independent identity store. Correction accepted; ranking unchanged.

## Preferred choice

**Final ranking: 3 > 4 > 1 > 2.** Option 3 — open-source alternative — with **Akeru as the lead candidate to spike** and **noid as a second candidate inside the same option**. One primary path. No parallel shim or reconstruction implementation.

**Why option 3 remains first.** It is the only option that already ships a named local bot profile with provider connections, clients, groups, plugin/MCP lifecycle, memory files, still-image generation and a WhatsApp DM channel under MIT. Those are expensive, undifferentiated parts of the product, and they are more than option 4 has today. The debate removed some of the assets I had counted — delegation is not resume, skills are provider-scoped, usage is partial, routing is per-bot, auto-deletion is a constraint — but it did not remove the shipped surface. The primary goal is not met by stock Akeru; it is a base to extend.

**Why the runner-up (option 4) loses.** DIY can implement every priority natively: a canonical `SKILL.md` library, a task route record with acceptance criteria, checkpoints before external writes, exclusive parent/child usage, a reviewable observer and a task-rating object. It loses because it must first build the commodity layer — clients, profiles, groups, provider sessions, plugin/MCP lifecycle, approvals, background service, WhatsApp channel, image tool and usage ledger — before it reaches the differentiators. The debate narrowed the margin: option 3 does not supply routing, resume, accounting or the observer for free either. If the spike shows the option-3 changes touch controller selection, accounting and skill registration and require a second authority for retries, option 4 becomes the smaller long-term burden. That is a real conditional, not a rhetorical caveat.

**Why option 1 is third.** Grok Bot is cloud-only and Cursor-managed, with no customer-facing model picker and usage recorded as Grok Bot usage rather than by model (V13). The shim documents only Codex OAuth, an OpenAI-compatible endpoint and a canned stub, uses an isolated profile and does not mention connected apps (V14). Hosted connector tokens stay on Cursor's backend. The isolated profile may restore the existing team and connectors — that is a genuine short-term bridge and should be tested — but it does not make option 1 the provider-independent identity store, and it cannot supply the required per-task routing, accounting or observer. Its possible retention of official video/WhatsApp connectors is a real effort saving while the vendor account works; it is not a foundation for the full priority set.

**Why option 2 is last.** The repository is archived, has no SPDX licence, targets macOS Apple Silicon with Node 26.5 and Xcode CLT, and is a 0.18 snapshot while the current product is at 0.75.x. No import from the current account is documented. The media status is unverified rather than “not supported,” but that correction does not move the archive/licence/platform facts.

**Did the debate change my position?** The order did not change; the confidence and the conditions did. I no longer describe the remaining work as a bounded policy layer. I withdraw variant dispatch as a primary-goal solution. I revise DEEPSEEK-6 from “tool calling undocumented” to “wire-format and live-reliability dependency.” I accept that external-write resume is custom. I accept that shim migration is conditional. I accept noid as a real candidate. I accept per-driver skill registration as the planning assumption. I accept the original video/WhatsApp-connector evidence. The debate produced no verified mechanism that makes option 3's extension cheap, and it produced no evidence that option 4 can reach a usable product sooner. The recommendation is therefore “spike option 3 first,” not “adopt option 3 as the solution.”

**Strongest objection to my own choice.** If per-task routing, neutral skills, external-write resume and parent/child accounting each require changes in Akeru's controller/accounting layers, the retained value is clients, profiles, groups, MCP/plugin switches, images and WhatsApp DMs — valuable, but not the differentiators. A small DIY composition around official harnesses and MCP libraries could then be the smaller long-term burden. I have not measured that threshold. The honest position is: option 3 is preferred on current evidence, conditionally, because it starts with more working product; the spike decides whether the retained product is worth the adaptation.

**Confidence.** Medium-low that Akeru is the better base before the spike; high that options 1 and 2 are not the primary path for the full priority set; low that stock Akeru satisfies skills, routing, safe resume, phone, video, shared pages, ratings and the observer together. These are qualitative confidence labels, not scores.

## What would change my mind

These are bounded comparison tests proposed for HUMAN's choice, not a specification and not permission to spend or connect accounts. No test has been run.

1. **Continuity on one bot, not a variant.** One named bot with a private remembered fact, a procedure, a goal, one `SKILL.md` and a partially completed task moves Codex → Claude → DeepSeek → Grok and back. Record the model/transport/auth class, whether the skill is discovered and executed, whether memory and tool set survive, and whether the next action repeats an external write. If persona, memory, skill or task state drops and the fix requires a core fork plus a second orchestrator, option 4 becomes preferred.
2. **Safe external-write resume.** Use a stub service with an observable ledger. Interrupt after acceptance and before acknowledgement, restart Akeru, and invoke `Try again`. The ledger must stay at one write, or the run must stop and report the outcome as unknown. If Akeru repeats the write and a short harness wrapper passes with a ledger, option 4 moves ahead for the primary goal even without the room UI.
3. **DeepSeek tool transcript and wire format.** Send a transcript containing an earlier assistant tool call and tool result, then ask for the next action, once through Akeru's DeepSeek preset and once through Claude Code with `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`. If only the harness sees the tool result, label the preset text/single-shot until an adapter exists and keep option 3 first only if that adapter is smaller than a new client. Record live streaming/parallel-call behaviour and the billing route.
4. **Skills discovery per driver.** On a clean Akeru install, add a unique `SKILL.md` bundle to `.claude/skills`, `.agents/skills` and any Akeru root. For Claude, Codex, Grok and a DeepSeek Custom API bot, check whether it appears in the `$`/`/` menu and whether invocation loads the instructions and dependencies. Then change provider on the same bot and repeat. If only a provider catalog exists and there is no supported registration hook, option 3's neutral-skill requirement needs per-driver changes or a fork; option 4 gains.
5. **Per-task routing on one bot.** Ask for a stronger model on the next task without creating a second bot and without hand-editing the profile. Record the files that changed and whether the task transcript survives. If the only path is hand-editing the saved model and starting fresh, per-task routing is not native; if a supported shared-memory delegation exists, the variant objection weakens. If the change requires controller edits and a second accounting authority, option 4 gains.
6. **Deletion safety.** Find a documented setting or a bounded patch that disables the seven-day archive deletion, and prove an archived bot survives. If it requires a standing fork, count it in the fork tax under the no-deletion rule. Do not archive or delete any bot, image or data in a comparison trial.
7. **Complete exit and restore.** Export bots, memory, routines, skill assignments, usage history, files and checkpoints; restore on a second environment and verify no silent omission. If only the main archive plus a separate memory export exists, reversibility is lower than “local files” suggests.
8. **Option 1 bridge test.** Run the shim against its isolated profile and check whether the ten named bots, four rooms, the Fuel Atlas page, the Weekly bot scorecard routine and the hosted connectors appear and work. A positive result makes option 1 a credible short-term bridge and a useful UI/connector reference; it still does not make it the identity store. A negative result removes its main advantage.
9. **noid trial inside option 3.** Test agent-file import, per-session model choice and retry with another model, and one stub write surviving a model change on Linux. If it reproduces and Pi Durable is stable enough, noid could become the option-3 lead; if not, Akeru remains the lead candidate.
10. **Subscription transport terms.** Establish whether ChatGPT, Claude and Grok subscription credentials may be used through Akeru's built-in runtime and, separately, through the shim/CLI routes. If vendor terms forbid it, option 3's cost/usability advantage shrinks to API-key routing, and the comparison with a thin CLI wrapper or DIY changes.
11. **Original connector reality.** Obtain the user's installed Grok Bot connector inventory and the actions actually used. If the team depends on hosted connectors with no reasonable MCP/API equivalent, option 1's bridge value rises; it still does not satisfy provider-independent identity, routing or accounting.
12. **A HUMAN priority change.** If exact UI and live-team continuity outrank provider independence, option 1 could be the pragmatic short-term choice. That would be a deliberate trade of the primary goal, and I would want it recorded as such. I do not infer it.
