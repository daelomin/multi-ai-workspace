### Declaring and customising a bot

**Option 1.** Install Grok Bot, clone the shim, `npm ci`, `npm run setup` (local TLS plus runtime extraction), configure `models.json` and `.env`, `./run-all.sh`. Bot creation is then the official app's flow inside the isolated profile: create a bot, name it, describe the job, connect apps when asked. Templates, if that profile can reach them, are one link plus plugin re-authentication, and they omit custom MCP. Appearance, rooms, and routines are the official UI. The gap is that this profile is not documented as a copy of the existing account, and model choice is a shim file rather than a per-bot library field.

**Option 2.** On an Apple Silicon Mac: Git LFS, `npm ci`, `npm run bootstrap`, `npm run package`, open the reconstructed app. Router settings choose Cursor, Claude Code, Codex, or OpenRouter for new turns. Bot creation is the 0.18 UI. There is no documented template library and no documented way to import the 2026-10-24 roster. Customisation of the current product's Pages and routines is outside this snapshot.

**Option 3.** Connect a provider under Settings → Providers (device code or API key). Create a bot, or walk the short setup: one sentence of intent, a proposed plan, a name, a first message. Skip setup is available. The profile panel edits avatar (shaped color and face), name, label, description, model, reasoning, voice, and tools, then Save. Instructions are the profile text. Lasting notes are per-bot `USER.md`, `MEMORY.md`, and per-group `GROUP.md`, with separate durable facts and approval for shared facts. A room is a group: name, boss, at least one other bot. A routine needs a procedure, schedule, timezone, required skills, and connectors, and the procedure must be approved before the schedule runs. There is no documented catalog of pre-named agent templates. Cloning "Natalia" as a template means creating another bot and copying instructions by hand. Memory does not follow the copy unless exported and imported. That is the right split between template defaults and instance memory, and the copy step is manual.

**Option 4.** No declaration flow exists. A friendly one would be: pick a named template, set instance name and appearance, edit procedures, goals, attitude, and skill selection, then connect credentials the template declares. Instance memory and task state would be new directories, not copies of the template. That flow can be the best of the four, after the product exists. Until then the step count is "design and build the product."

### Autonomy, silence, collaboration, observer

All four can host a policy. None of them, as documented, already implement HUMAN's observer.

- **Autonomy.** Official routines and the local computer approval policy are the mature version of "act, then stop for send/pay/delete." Akeru's local default is Auto review: safe actions continue; send, pay, delete, production changes, secrets, and unclear intent still ask. Helpers cannot ask the user. DIY has no policy until one is written. Option 1 keeps the official approval UX if the official host is what is running. The shim README does not document an approval service of its own.
- **Silence.** Official guidance says to avoid broad event listeners because they create noise and spend usage. Akeru posts short status notes after meaningful progress, and channel replies send the final reply only, with tool output staying inside Akeru. Akeru's silence watchdog is a 90-second "provider sent nothing" detector. It is not a decision to stay quiet. Deliberate silence has to be an instruction plus a gate on every path. The screenshot's silence request is evidence that HUMAN already wants that gate. It is not evidence the live bots have it.
- **Collaboration.** Official bots message each other on a shared cloud computer that is one security boundary. Akeru groups have a boss, `@` mentions, and delegation cards. People cannot be added to a group. DIY can copy either shape. Excellence-driven challenge is a prompt and review rule on top of all four. Nothing in the sources implements peer critique.
- **Observer.** A separate bot that proposes changes to strategy, procedures, goals, skills, and communication is new work on every option. Akeru's Usage page already shows "Observer" and "Reflector" tokens. The usage doc defines those as internal memory stages (recall and extraction), billed inside the parent entry. They are not a strategy reviewer, and they must not be presented as one. Observer cost is extra model turns, and it should be visible as review overhead. Proposed edits to goals or persona stay pending until a person accepts them. Auto-applying them would violate the priority on every option. Usefulness depends on evidence: task ratings, rework, and linked deliverables. Without that evidence the observer only has chatter.

### Good-enough routing and safe switching

These are the critical features, and they cut against every current product default.

Official Grok Bot: Cursor selects the model. The user cannot express "this task needs a stronger model" as a product control. Credit exhaustion, rate limits, and auth failures surface as product limit messages; the fetched security page does not show per-model attribution. A cheaper mix can change with no fixed vendor set. That fails the rule that cheaper must not silently lower quality.

Option 1: `models.json` can name a Codex OAuth model and an OpenAI-compatible model, with an optional `fallback` used when Codex authentication or quota rejects the request. The README does not define capability failure, partial tool success, or what happens to an in-flight computer action. Fallback is not a quality decision. User-initiated switching is editing `models.json` or the app's model setting. Account visibility is the provider's own UI. The shim does not document a unified credit balance.

Option 2: the router chooses the backend for new turns. Maintainer says tool execution is preserved across Cursor, Claude Code, Codex, and OpenRouter. No checkpoint, idempotency key, or duplicate-side-effect rule is in the README. Local token totals are activity records. DeepSeek is absent. Claude Code and Codex here are CLI logins, which is a different route from an API key.

Option 3: the model is saved on the bot. "Akeru never switches it for you." When the plan hits a limit, Send stays off until the user waits, raises the cap, or switches provider. Backup accounts are the same provider: the request that hit the limit still fails; the next request uses the backup. A provider that reroutes a message can show `Model rerouted from … to …`, except providers on Akeru's session controller, which do not report the effective model. Changing provider starts a fresh session with the same tools. Resume exists for an interrupted request; it is not documented as cross-provider resume. Delegation to another bot is the practical way to put one task on a stronger model. The card shows tokens and access. It does not document idempotency of tools the first bot already ran. Subscription meters and estimated cost are separate. A cost estimate is "not money spent." Disconnected and unreported limits stay hidden. This is the best visibility of the four products, and it still does not attribute a parent turn and a child helper without a careful reading: helper work does not appear as its own chat, and tool or routine boundaries are zero-token lifecycle entries whose model tokens stay on the surrounding turn. Whether a helper's tokens are also inside the parent's reported total was not tested. Assume double-counting is possible until a spike prints both numbers for one delegated turn.

Option 4: the only place a task record can require acceptance criteria, a readiness check, a chosen route, and a reason before any spawn. Credit exhaustion, rate limit, auth failure, and "model cannot meet the criterion" can be different states because we would define them. Checkpoints and idempotency keys can be required before a retry. Provider APIs that do not return remaining subscription credits still cannot show a balance. Automatic fallback and a user-initiated switch can share one resume path. That design is reasoning, not an existing system.

Specification-readiness, for every option, is a gate in front of execution: purpose, scope, exclusions, interfaces, constraints, bounded subtasks, and checks a person can run. A long prompt is not that gate. Exhausted credits are not a reason to lower the gate. No numeric budget is assumed. The lean UI should show the flag, the uncertainty, the route, and the reason before a cloud agent or helper starts. Re-triage when scope or evidence changes. Option 3 can hang this on delegation and routines. Option 1 can hang it on the official app only where we control the prompt, which we do not fully control. Option 4 can refuse to dispatch. Option 2 has no documented hook.

### Existing team, UI, task ratings, usage

The baseline to preserve is names and roles, room-shaped collaboration, shared result pages, and routines, with room to add bots later.

- Option 1 preserves the live official workspace if HUMAN keeps using the normal profile. The shim's documented launcher uses an isolated profile and does not modify the default profile, so "run the shim" and "keep Natalia's room" are not the same configuration. Which state is local versus still synced to the account is unverified.
- Option 2 can look like an old Grok Bot. It is not evidence the current rooms, the Fuel Atlas page, or the weekly scorecard routine exist in 0.18 or can be imported.
- Option 3 can recreate names, avatars, instructions, groups, routines, and delegation. Shared Pages have no counterpart in the docs fetched. Import of an official persona is not documented. Akeru's own archive omits memory and routines. Expect manual entry for the ten visible names and four rooms.
- Option 4 can model all of it and imports nothing automatically.

UI direction: the screenshot is a lean roster, conversation, and shared results. Option 1 matches that look when the official UI is on screen. Option 3 has a roster, pins, a conversation, a collapsible bot panel, and a separate Usage page. That can hold compact task and usage summaries with drill-down. A dense dashboard would be a misuse of the Usage page, not a requirement. Option 2 is the 0.18 look. Option 4 has to be designed against the screenshot on purpose.

Task ratings: no option stores "the consuming bot rates this task" with reviewer identity, criteria, reasons, deliverable links, difficulty, insufficient evidence, and later correction. Akeru work cards are the nearest evidence object (who did the work, access, tokens, result excerpt). They are not a rating. Self-ratings, mutual praise, and scoring chatter are product rules, not features to turn on. Reputation of a bot should stay a separate aggregate, if it exists at all, and this proposal should not invent the formula.

Usage transparency: official views are Grok Bot usage, not by model. Option 2 records local request and token totals when the provider returns them, and says they are not an invoice. Option 3 separates plan meters, estimated cost, per-bot input and output, Observer and Reflector, subscription pool, reserved tokens, and "Unavailable" or a trailing `+` for partial data. It does not document per-room, per-task, and parent/child totals with child usage excluded from the parent rollup. Reasoning and cache tokens appear only when the provider reports them; the usage doc says a later cache correction must not count the turn twice. Option 1 and option 4 have no such page. Option 4 can define the rollup. None of the options can show exact subscription dollars they do not receive.

### How the priorities move the ranking

The primary goal eliminates "keep the official client and hope" as a sufficient answer. Official model selection is Cursor's, usage is not per model, and connector tokens do not travel with a local UI. Option 2's router is the right shape and the wrong generation: archived, unlicensed, macOS, 0.18 versus 0.75.5. Option 3 already stores the bot apart from any one provider and already speaks Claude, Codex, and Grok subscriptions, with DeepSeek as an explicit API-key preset. Option 4 would store it more cleanly and does not exist.

Usability favors option 1 only for someone who stays inside the official app, and favors option 3 for someone who will recreate the roster once. Cost of inference is mostly the same providers on every path. Option 1 adds protocol-maintenance cost. Option 2 adds a Mac and a frozen tree. Option 3 adds fork maintenance and optional brokers. Option 4 adds the most build time, which is the cost that delays a working team.

Specialists are custom on every honest path. WhatsApp messaging is the one specialist Akeru already wires, and even that is DMs, not account administration. Phone and short movies are custom everywhere. That tie should not decide the platform.

## Preferred choice

**Option 3, Open-source alternative, with Akeru Bot as the candidate to test and extend.** One primary path. No parallel shim and no parallel 0.18 reconstruction.

What Akeru already is, in maintainer docs: a local bot profile (name, avatar, instructions, model, tools, memory), groups, routines, delegation cards, provider logins for Claude, Codex, and Grok, a DeepSeek Custom API preset, plugin and MCP attachment, a usage page that refuses to pretend estimates are invoices, and a WhatsApp Cloud API channel for direct messages. Those are the expensive, undifferentiated parts of a persistent-bot product. The MIT license and the 2026-10-23 push make it a maintainable base in a way the archived reconstruction is not. It runs without a Grok Bot binary, which keeps it clear of the extraction and "no upstream license" problems in options 1 and 2.

What still has to be added on that base, in this order, and only after a spike proves the hooks exist:

1. A canonical `SKILL.md` library, projected into the directories Claude Code, Codex, and Cursor actually scan, and injected as instructions for routes that have no scanner (DeepSeek Custom API, Grok subscription if it does not read those directories).
2. A per-task route record: acceptance criteria, readiness check, chosen model and provider, and a reason. Credit exhaustion, rate limit, auth failure, and insufficient capability stay different outcomes. A cheaper model is not selected by silence. The bot's saved model remains the default, and a departure from it is visible.
3. Checkpoints and idempotency keys before a provider change or a retry, so a second backend does not repeat a side effect.
4. An observer bot whose proposals are reviewable diffs. It does not write goals, persona, or skills by itself. Its tokens show up as review overhead. Akeru's Observer/Reflector memory meters are left named as memory.
5. Task ratings on the work card: reviewer, criteria, reasons, links, difficulty, insufficient evidence, correction. No self-score.
6. Specialist adapters: a voice API for real phone calls, WhatsApp administration only for the operations HUMAN lists later, image, and short video. Messaging WhatsApp stays the channel that already exists.

**Why option 4 loses.** It can be the cleaner expression of neutral skills, per-task routing, and checkpoints. It loses because that expression includes rebuilding profiles, groups, provider sessions, plugins, clients, approvals, and usage meters that Akeru already documents. The comparison is "policy layer on Akeru" against "policy layer plus the platform." DIY wins when the spike says the policy layer cannot sit beside Akeru's core.

**Why option 1 loses.** Familiar UI and the live roster are real advantages, and they answer a different goal. The official security doc says Cursor picks the model and does not attribute usage by model. The shim's documented routes are Codex OAuth and OpenAI-compatible chat completions, and user-visible speech depends on `SendMessage`. Connector tokens stay on Cursor's backend. The launcher's isolated profile is not a migration of the current team. Keeping option 1 as a bridge would be a second product, with a second state store, which is the hybrid the proposal recommended and this review rejects.

**Why option 2 loses.** The router and the "tools across providers" claim are the closest idea to the primary goal, and the repository is archived, unlicensed, and pinned to macOS 0.18.0 while the product changelog is at 0.75.5. It cannot be the base for this Linux host or for the current Pages and roster.

**Strongest case against option 3.** The README forbids publishing the fork unless Leo asks, the project is pre-1.0, and 70 issues are open. Skills and failover follow the provider, and the product refuses silent model switches. If per-task routing, neutral skills, or safe resume require a standing fork, the maintenance cost becomes Akeru's plus ours, and option 4 is the smaller long-term burden. There is a second, product-level objection: DeepSeek is an API-key preset, tool calling on that preset is unverified, and subscription credit balances are only as visible as each provider's meter. A router that switches providers on quota must be explicit and tested, or it will duplicate side effects the current "fresh session" rule does not prevent.

**Confidence: medium.** High that options 1 and 2 are the wrong primary for the full priority list. Medium that Akeru is a better base than DIY before a spike. Low that Akeru, unmodified, satisfies skills, routing, resume, phone, video, or shared pages.

## What would change my mind

1. **Continuity spike fails.** One named bot, one `SKILL.md`, one memory note, one routine. Run a task that writes a file once on Codex, then continue the same task on Claude, Grok, and DeepSeek. If persona, memory, skills, or tool state drop on the switch, and the fix is a core fork rather than a local adapter, option 4 becomes the primary.
2. **Routing spike fails.** If a task cannot carry its own model without a second bot and a second uncheckpointed tool loop, and that workaround double-fires side effects, option 4 becomes the primary.
3. **Skill spike fails.** If Claude, Codex, and a DeepSeek Custom API bot cannot be shown a projected `SKILL.md` through a supported path, the skills priority is unmet on option 3.
4. **Governance.** If the fork's license practice or the "do not publish" line blocks the patches we would need, or upstream movement makes rebase unrealistic, switch the option 3 candidate or move to option 4. Another platform is still option 3 only after the same matrix is filled from its docs.
5. **HUMAN ranks pixel-level continuity with the current account above provider-independent identity.** Then option 1, using the normal profile and accepting Cursor-managed models, matches that ranking. That choice should be written down as a decision to defer the primary goal. I would not infer it.
6. **The live connector set cannot be reattached.** If the useful work of this team depends on hosted connectors that have no MCP or API equivalent at an acceptable setup cost, option 1 remains a temporary bridge for those connectors only. It still does not become the identity store.
7. **DeepSeek must be a subscription CLI harness with its own skill directory, and Custom API tool calls fail a small test.** Then option 3's DeepSeek story is an API route only, and the primary goal is only partly met until an adapter exists. If that adapter is large, option 4 gains.
8. **A tested export of the current personas, memories, and routines appears.** Any option that can import it without transcription moves up on usability. None can today, on the evidence fetched.
