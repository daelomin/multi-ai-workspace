# CHATGPT — round 2 independent option assessment

Checked 2026-10-24. Recommendation for HUMAN's choice, not implementation approval. Read README.md, workflow.json, spec.md v0.1, assessment-context.md and both round-1 reviews. No decisions.md or earlier consolidation was present. No round-2 peer file was read. No candidate was installed, credentials inspected, connector authenticated, paid request submitted or end-to-end behavior demonstrated.

**Recommendation: option 3, Open-source alternative, with Akeru Bot as the lead candidate for comparison testing.** Its named bot profiles and independent provider connections are a better starting point for HUMAN's persistent-bot goal than preserving the official UI. Confidence is moderate in the path preference, low in complete requirement satisfaction. None of the four paths currently has evidence of safe, quality-preserving continuation across every requested backend.

### Declaring bots, templates and skills

The common usability trial should start from a named template, for example “Mori — researcher,” create “Mori / travel,” change its avatar/outlook, attitude, procedures and goals, select its skills, connect dependencies, and complete one useful task. This is a proposed example, not an assertion that a candidate ships that template. Create a second instance and prove that it inherits defaults without inheriting the first instance's memories or credentials.

**Verified file conventions:** [Agent Skills specification](https://agentskills.io/specification) uses a directory with singular **SKILL.md**, YAML name/description, optional scripts/references/assets. [Codex skills](https://learn.chatgpt.com/docs/build-skills) discovers local .agents/skills roots and supports explicit enable/disable configuration. [Claude Code skills](https://code.claude.com/docs/en/skills) uses SKILL.md bundles, including .claude/skills. Akeru's [composer guide](https://raw.githubusercontent.com/opencoredev/akeru-bot/main/docs/user/composer.md) describes provider-specific catalogs and invocation; inspected [ClaudeSkills.ts](https://github.com/opencoredev/akeru-bot/blob/main/apps/server/src/provider/Drivers/ClaudeSkills.ts) scans SKILL.md roots, while [GrokSkills.ts](https://github.com/opencoredev/akeru-bot/blob/main/apps/server/src/provider/Drivers/GrokSkills.ts) queries a CLI catalog. These inspected drivers do not prove every newer built-in subscription route uses the same machinery. No candidate is verified to discover literal plural SKILLS.md automatically. Satisfying HUMAN's requested capability requires compatible discovery and execution, not renaming a file and assuming it works.

For option 3, [OpenClaw skills](https://docs.openclaw.ai/tools/skills) and [failover](https://docs.openclaw.ai/concepts/model-failover) provide an additional existing-platform comparison: documented skill directories and error-aware failover are useful counterevidence to any claim that all such infrastructure must be custom-built. I keep Akeru as lead because of the evidenced bot setup experience; OpenClaw's present installation and its template workflow were not tested. This is a candidate within option 3, not a fifth path or a proposal to combine two full runtimes.

**Reasoning for every option:** retain identity/persona, authorized goals, procedures, skill versions, memory and task progress outside any one provider session. Resumption needs confirmed results, outstanding actions and dependencies, not private reasoning traces. Validate schema support, context limits, images/files, tool-result pairing, cancellation and permission scope before handing off. A changed model cannot inherit an unsupported tool by name alone.

A credit-exhaustion response may permit another funded route; a rate limit may call for waiting; an expired/revoked credential needs reconnection; inadequate task performance needs a more capable model or HUMAN. They should produce distinct evidence and behavior. None of these candidates demonstrates universal live account-credit visibility. A model list or zero-cost health check does not establish remaining credits or entitlement to a successful tool-using turn. HTTP status alone is insufficient when providers encode different causes in response bodies.

Retrying inference is different from retrying a side effect. After an uncertain response to a phone call, WhatsApp send or event creation, first reconcile the service's returned identifier/status or searchable operation record. Where the service offers no reliable deduplication/reconciliation, pause the ambiguous action instead of resending it. This requirement applies equally to manual and automatic provider changes; automatic fallback increases exposure because no person necessarily notices the boundary.

For all options, the useful observer compares task success, tool errors, unnecessary escalations, rework, message usefulness and observed cost/latency. It proposes a specific procedure/strategy/skill change with evidence, tests against representative held-out tasks, and retains or rolls back the change based on outcomes. It must not silently edit HUMAN's goals or persona. Sample completed/failed tasks and batch proposals rather than running a second model on every token or reviewing other observer reviews recursively. Silence means no user-visible message when nothing useful changed; a quiet task can still retain an auditable result. Expose conclusions and evidence, not private deliberation traces.

## Preferred choice

**Option 3 — Open-source alternative**, lead candidate **Akeru Bot**, without a parallel reconstruction or shim track. It already addresses named instances, user-facing customization, local state and multiple provider connections, while offering a path to reuse service MCP/APIs. Those directly serve HUMAN's primary goal and usability priorities. The specialist integrations and quality-routing gaps still require work; open source does not make them free or complete.

**Strongest case against my choice:** Akeru explicitly starts fresh provider sessions, does not automatically switch an unavailable model, exposes provider-dependent skills, and excludes essential data from its general archive. Its subscription transports are maintainer claims, not blanket vendor certification. A complete named-template library and behavioral silence/observer loop are not demonstrated. If fixing these means replacing its coordinator, memory and driver layers, the reuse argument collapses and DIY may be cleaner. Its documented automatic deletion of archived bots after seven days also conflicts with this workspace's explicit no-deletion-without-named-authorization rule; that behavior must be disabled/changed before adoption here, not exercised in a trial.

**Closest runner-up: option 4 — DIY primitives.** It loses because today's proposal provides no integrated runtime or friendly bot-declaration flow, and HUMAN values usability, total cost and functionality together with control. Constructing those capabilities before obtaining evidence of quality or continuity is a larger unmeasured commitment than testing an existing platform. It would win if Akeru's boundaries prevent safe continuity or the required authorization model cannot be respected without a deep rewrite.

Option 1 is attractive for familiar UI and its reported Linux/Codex loop, but HUMAN's leading requirement is persistent bots across providers; undocumented host coupling and unknown connector access add dependencies exactly at that boundary. Option 2 offers more runtime editability and reported multi-route tools, but archived/macOS-oriented evidence and retained renderer constraints make its long-term maintenance case weaker. I do not recommend the proposal's shim-first plus parallel reconstruction hybrid: duplicate runtimes increase validation and state-migration work without proven connector or continuity benefit.

## What would change my mind

These are bounded **comparison tests proposed for HUMAN's choice**, not a full implementation specification or permission to spend/connect accounts. Test the same tasks and observable outcomes on each viable candidate; retain failures and unknowns rather than invent scores.

1. **Actual access and continuity:** One named bot, with a private remembered fact, procedure, goal, skill assignment and a partially completed task, moves through Codex, Claude, DeepSeek and Grok and back, then survives restart. Record exact model, transport, credential class and billing basis for each hop. Test manual switching first, then simulated exhaustion. Verify supported subscription routes with vendor documentation and an entitled turn, not a model list/login alone. A supported shim/reconstruction route with full continuity could reverse my preference.
2. **Safe tool continuation:** Use a stub external-write service with an observable action ledger. Interrupt before submission, after acceptance/before acknowledgement, and after acknowledgement; simulate quota exhaustion, rate limit, expired login and inadequate model capability separately. Require one intended action, correct status reconciliation, preserved permissions and honest reporting of ambiguity. Repeat with incompatible tool schema/context/media requirements. A candidate that resumes chat but repeats the action fails this comparison.
3. **Good-enough model evaluation:** Use representative tasks: factual inbox summary, timezone-sensitive calendar change, structured tool call, a coding task with an independent check, a phone interaction script, and an image/video request. Define output/task checks before running: correct facts, dates and recipients, valid schema, verified external result, preserved authorization and adequate media output. Record success/failure, retries, human interventions, latency and actual reported spend. A cheap model must meet the same checks; uncertainty or failure triggers a stronger route rather than lowered quality. Human review or an independent check validates subjective results; self-confidence alone is not calibrated evidence.
4. **Friendly library:** Run the Mori template-to-two-instances example with a non-developer. Observe steps, confusion, missing dependencies and time without inventing a target benchmark. Verify per-instance appearance, persona, goals, procedures, skill discovery/invocation and memory isolation. Demonstrated template reuse on a competing path could outweigh Akeru's profile editor.
5. **Connector inventory and specialist reality:** Obtain the user's actual service/tool names and actions, then fill the unknown original rows and authenticate only authorized test accounts. Demonstrate read and authorized draft/test-write workflows for each needed productivity integration; phone conversation versus microphone chat; WhatsApp messaging versus separate sender/profile/template/admin actions; image edits and a completed short movie. Record credential custody, callbacks/always-on requirements, supported region and actual costs. A retained hosted connector route materially reducing this work could make option 1 the winner. Full Business administration remains unresolved until its precise operations are named and evidenced.
6. **Silence, collaboration and observer:** Replay a useful update, repeated update, routine success with nothing new, meaningful blocker and a mistaken peer claim. Measure whether the bot acts quietly, asks once when needed, corrects with evidence and avoids duplicate conversation. Give the observer a real failure and test its proposed procedure change against held-out cases; it must not alter persona/goals without authorization. Record its extra calls/tokens and whether it improves outcomes. A chatty default or ineffective observer is a material cost/usability failure, not cosmetic.
7. **Operations and exit:** Export/restore the whole working bot state, including the pieces outside a general archive; prove it on a second supported environment. Check sleep/restart behavior, update compatibility, actual maintenance ownership and the no-automatic-deletion constraint. If option 3 needs substantial coordinator replacement or cannot preserve/transfer required state, prefer option 4. If a maintained, independently authorized reconstruction/fork demonstrates these properties on the target machine with lower observed setup/maintenance burden, reconsider option 2.

Decision-relevant unknowns remain: actual Grokbot inventory; exact target OS/resources; supported subscription entitlements/transports; continuity at uncertain side effects; complete skill dependencies across providers; template-library maturity; full WhatsApp administration scope; task-quality evidence; workload/region-based service costs; and maintenance/export completeness. HUMAN's goals and deletion rule are fixed; this recommendation is challengeable.
