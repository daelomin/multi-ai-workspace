## Primary-source findings

1. [Official computer and apps documentation](https://docs.x.ai/grok-bot/computer-and-apps) says connected apps are plugins, connected apps are account-wide, and OAuth tokens stay on Cursor's connector backend rather than the Bot computer. **Inference:** moving the UI, model or computer locally does not by itself move that connector backend or grant access to those tokens. Examine whether a candidate retains a supported hosted path, supports independent MCP services, or needs new authentication/integration work.
2. [Original reconstructed runtime README](https://github.com/b-nnett/grok-bot-0.18-reconstructed/blob/main/README.md) documents Cursor, Claude Code, Codex and OpenRouter inference routes and reports MCP/plugin tool execution across routed conversations. It also documents an optional local Docker sandbox. This is evidence that model routing and a tool bridge are plausible, not proof that every contemporary connector, tool action, subscription entitlement or OS works locally. The source README's original requirements are macOS/Apple Silicon; do not silently assume Linux or Windows parity. Distinguish the specific forks named in the proposal.
3. [Linux shim README](https://github.com/luckeyfaraday/grokbot-shim/blob/main/README.md), fetched through GitHub (blob SHA `3fa860e2b1f6758d57239cb0ee4a3afde28dd02d`), reports local agent lifecycle, streaming tool calls, Codex OAuth, compatible model endpoints and a local computer desktop. It depends on installed application runtime extraction and undocumented integration points. Its listed working features do not establish full hosted-connector parity. Reliable tool calling matters: user-facing communication uses a SendMessage tool rather than ordinary assistant text in that host loop.
4. [Official template guide](https://x.ai/bot/guides/templates-for-grok-bot) describes reusable bot templates containing instructions, selected memories/skills and plugins. Recipients reinstall/authenticate plugins, and custom MCP servers, scripts and custom code are not automatically included. **Assessment implication:** a convenient agent library must also handle dependency discovery and user setup, not merely copy persona text.
5. [Official skills and routines documentation](https://docs.x.ai/grok-bot/skills-routines-and-automations) distinguishes reusable task instructions from scheduled/event-driven runs; skills may need connected-app access. Event-trigger integrations are separate from ordinary service apps. **Assessment implication:** evaluate skills, schedules, event delivery and credential setup separately; a connector inventory alone cannot demonstrate autonomous behavior.
6. [Twilio Call resource](https://www.twilio.com/docs/voice/api/call-resource) documents programmable phone calls. [Twilio WhatsApp Business Platform](https://www.twilio.com/docs/whatsapp) documents messaging, sender registration, account/profile-related guides and templates. These are examples of public integration routes, not a choice of vendor and not evidence that a Grokbot connector already exposes them. Check the specific operations needed, supported regions, account onboarding, recurring fees, usage fees and whether a direct provider API is preferable. No phone call or customer message has been made.
7. [Image generation API](https://docs.x.ai/developers/model-capabilities/images/generation) and [video generation API](https://docs.x.ai/developers/model-capabilities/video/generation) document external media-generation routes. Availability of an API does not establish a bundled local tool, media workflow quality, affordability, or local/offline support. Compare alternative providers and local generation where relevant. No media-generation job has been submitted.

## Lean UI, peer accountability and usage visibility (HUMAN, 2026-10-24)

The screenshot is the graphical reference: lean and efficient. Preserve an uncluttered bot/room workspace with conversation and shared results; compare compact task/usage indicators and progressive disclosure rather than assuming a dashboard-heavy redesign.

HUMAN wants bots to rate other bots' tasks based on how much the work solved their issues, how much rework was required, output quality and efficiency. Assess ratings as evidence about an individual task and its downstream usefulness, not popularity. Include recipient/reviewer identity, acceptance or remaining issues, links to outputs and revisions, reasons for a rating and the cost/time context where available. Discuss how ratings can be challenged or corrected and how to distinguish difficult work, changed requirements and genuinely avoidable rework. Do not invent a numeric weighting formula before HUMAN chooses a path; compare candidate support and tradeoffs. The observer should use this evidence to propose strategy refinements, and the cost of reviewing must itself be visible.

HUMAN also requires clear token usage for discussions, tasks and spawned cloud agents. Evaluate traceability from room/discussion to task to bot/model/provider turn and spawned child agents, including retries, fallback attempts, and observer/critique activity. Show both exclusive cost and rolled-up totals without counting child usage twice. Separate measured and estimated usage, unavailable telemetry, API billing and subscription/credit limits. Report input, cache and output counts, and reasoning usage only where exposed by the backend; do not count an included subcategory twice. Distinguish booked tasks from actual completed work and include coordination overhead in efficiency assessment. A cloud-agent spawn is a tracked unit of work with its own usage and result, not a hidden expense.

Each implementation option must explain what can be displayed natively, what instrumentation or integration is needed, which provider telemetry is unavailable and how the proposed UI keeps this understandable. This is assessment scope, not a selected architecture or a request to redesign the live Grokbot account. The new evidence arrived during round 2; challenge and response passes must revisit it.


## Early detection of large, complex and expensive tasks (HUMAN, 2026-10-24)

HUMAN requires early identification of very large or complex tasks before they quietly consume substantial usage. Complexity and cost are related but not identical: ambiguous requirements, architecture decisions, unfamiliar integrations, large context, external dependencies, long execution, difficult validation and expected rework all matter. Compare a lightweight initial triage and bounded discovery when the task cannot yet be estimated. State estimate ranges and uncertainty rather than inventing precision.

Assess two explicit routes: (1) use an advanced model for work requiring its judgment/capabilities; (2) specify the work thoroughly enough that a simpler model can implement the intended vision. Also compare advanced-model planning and review combined with simpler-model execution. Model adequacy is task-specific, not a permanent label or a blind response to exhausted credits.

For the specification-led route, assess readiness before handing off: purpose and intended outcome; scope and exclusions; relevant context and dependencies; interfaces, data/contracts and constraints; manageable subtasks and handoff boundaries; concrete acceptance examples and independent validation. Unknowns or major design decisions must be resolved or explicitly assigned, rather than passed to a cheaper implementer as if settled. Do not equate a long document with a usable specification, and do not assume any model can handle the task merely because it has a checklist.

Compare expected TOTAL delivery cost across routes: specification effort, model turns, spawned agents, tools, implementation, review, validation and likely rework. The lean UI should make the complexity/cost flag, estimate uncertainty, proposed route and rationale inspectable before substantial dispatch. Reassess when discovery or actual spend invalidates the estimate; use peer outcomes and observer feedback to improve later estimates and routing. No numeric thresholds, budgets or mandatory approval rules have been supplied by HUMAN, so explain candidate policy choices instead of silently imposing them.

This is an assessment requirement for the future system, not permission to begin full implementation specifications before HUMAN selects an option. Revisit this new requirement during the current debate's challenges and final responses.
