### DEEPSEEK-1 · The action ledger has no write-ahead ordering, so a sent action can be stranded in `intent`
**Severity:** major
**Finding:** AK-TSK-10 and `docs/04` §4.4 define `intent` as "action decided, not sent" and `dispatched` as "request possibly reached the provider", but no requirement states that the `dispatched` entry must be durably appended *before* the connector call. AK-TSK-14 reconciles only ledger entries in `dispatched`/`unknown`; AK-TSK-11 and the retry/fallback rules gate only on a `dispatched`/`unknown` action. An implementation that records `intent`, invokes the provider, and records `dispatched` after the call has begun (or after it returns) leaves a sent action recorded as `intent` if the process dies in that window. Startup recovery then ignores it and a later attempt can resend it — exactly the duplicate external effect the unknown/reconciliation rules exist to prevent. `action-record.json` covers only an action already in `unknown`. N3 fixed the post-dispatch guards but not this pre-record window.
**Proposed correction:** State the ordering in AK-TSK-10 and the executor contract (`docs/05` §5): persist `intent`, then durably transition to `dispatched` before invoking the connector. On recovery, treat an `intent` action whose attempt has ended as possibly sent (verify/reconcile; never auto-resend) unless the executor can prove the call was never made. Add a fault case for a crash between the send and the `dispatched` record and extend T-03/T-14.
**Evidence:** `spec.md` AK-TSK-01, AK-TSK-10, AK-TSK-11, AK-TSK-14; `docs/04-data-model.md` §4.4 state table; `docs/05-interfaces.md` §5 executor rules and §6 retry/fallback footnote; `docs/10-tests-and-acceptance.md` §3 F-08/F-17 and T-03/T-14; `evals/fixtures/action-record.json`. Static inspection only.
**Confidence:** high

### DEEPSEEK-2 · Kill switch and quarantine release are required but absent from the command contract
**Severity:** minor
**Finding:** AK-SEC-09 requires a kill switch that pauses all dispatch without losing state, and `docs/12` §7.7 and §7.10 instruct the operator to use it. AK-OPS-15 and T-14 require recovery quarantine to be released per task/routine/delivery with the release recorded. `docs/05` §1.5 declares its command groups "the implementation contract", but it contains no command to engage or release the kill switch and no command to release quarantine: `restore.apply` starts quarantine, `health.report` is read-only, and no other command records a per-item quarantine release. The scope, guards, authorization and audit record for both safety controls are therefore undefined.
**Proposed correction:** Add `dispatch.pause`/`dispatch.resume` (kill switch; global or bot/connector scope; preserves state; authorized actor; audited) and `quarantine.release` (task/routine/delivery; requires the stored reconciliation evidence; actor; audited). Add tests that release without evidence is rejected and that the kill switch blocks dispatch without cancelling work.
**Evidence:** `spec.md` AK-SEC-09, AK-OPS-15; `docs/12` §7.7, §7.10, §5.3; `docs/10` T-14; `docs/05` §1.5 (no such command).
**Confidence:** high

### DEEPSEEK-3 · Route records omit `auth_class`, and the role default ranks across auth classes
**Severity:** minor
**Finding:** AK-RTE-02 requires every route to be recorded with `auth_class` and `options` (and provenance); AK-TRG-10 and `docs/09` §1.7 allow cost ranking across auth classes only through the one labelled routing-comparison unit and only when policy enables it (U16 default off). The records that matter do not carry it: `RouteDecision.candidates` has no auth class, `UsageRecord.route` is `{harness, driver, provider, model, instanceId, accountLabel?}`, and `RouteSnapshot`/`StartTurnInput.route` omit it too; only `ProviderCapabilities` has `authClass`. The role default in `docs/04` §4.3 then assigns `specification-led` to "the lowest-expected-cost" floor-meeting candidate, which compares `estimatedCost` across all floor-meeting candidates regardless of auth class or cost unit — the cross-class ranking the default policy forbids. The comparison is also undefined for overlapping `MoneyRange`s (no point estimate or ordering rule). The fixture already mixes subscription-equivalent and price-table candidates and carries no auth class to check any of this. N4 added the role predicate but not its like-with-like guard.
**Proposed correction:** Add `authClass` (plus `options`/provenance) to the route snapshot, `UsageRecord.route` and each `RouteDecision` candidate; restrict the role default to within-class comparison (or apply the labelled comparison unit only when the policy enables it); define how overlapping `MoneyRange`s are ordered; add a fixture/T-10 case with candidates in two auth classes.
**Evidence:** `spec.md` AK-RTE-02, AK-TRG-10, AK-ACC-02; `docs/04` §3 `RouteDecision`, §4.3 role, §5 `UsageRecord`; `docs/05` §2 `StartTurnInput`, §2.1 `ProviderCapabilities`; `docs/09` §1.7 and §8 route view; `evals/fixtures/route-decision.json`.
**Confidence:** high

### DEEPSEEK-4 · `RouteDecision` candidate `support` is undefined and cannot prove the skill floor
**Severity:** minor
**Finding:** `docs/04` §3 defines `meetsFloor` to include "skill support >= requiredSkillSupport", but the candidate's separate `support` field (`"verified"|"assumed"|"unknown"`) is never defined and is not the five-level skill-support set. No candidate field records the per-skill support level used in the floor check. In `route-decision.json`, codex has `meetsFloor: true`, `support: "assumed"`, and a `requiredSkillSupport` of `native-verified`; under `docs/10` §4's invariant "no route with `meetsFloor: true` below the required skill support", either `support` is the skill-support state (so the fixture is inconsistent and `meetsFloor` is wrong) or it is not (so the validator has no input to check the invariant). T-02/T-10 route rationale has the same gap.
**Proposed correction:** Define `support` or replace it with a structured `skillSupport` (per required skill: mechanism, verified, evidence) that feeds the floor check; correct the codex fixture or its `meetsFloor`/note so the record and the invariant agree; add schema/validator coverage.
**Evidence:** `docs/04` §3 (candidate shape and comment), §2 (`SkillSupportEntry`); `docs/10` §4 fixtures/invariants; `evals/fixtures/route-decision.json`; `spec.md` AK-TRG-09 and AK-RTE-13.
**Confidence:** high

### DEEPSEEK-5 · AK-ACC-05 and AK-ACC-14 formulas contradict the normative worked example
**Severity:** minor
**Finding:** AK-ACC-05 says inclusive roll-ups sum "exclusive descendants plus the owner's own turn usage". The normative `docs/09` §4 inclusive is exclusive T-142 ($3.12 — which includes review, coordination, observer, tool and failed-attempt records) + child T-143 ($0.38) = $3.50; "owner's own turn usage" reads as T-142's category-`turn` records ($2.67) and would omit $0.45 of overhead and the tool/failed records. Separately, AK-ACC-14 divides by "the number of distinct accepted tasks in that cohort", while `docs/09` §9 says the denominator is accepted *roots* ("The denominator counts the same roots that were accepted"); an accepted child counts once under the root-only rule and twice (root + child) under AK-ACC-14's wording, and T-09's parent/child case checks only the numerator. The `docs/09` §9 code block and its following prose also disagree on this point, so the correction must resolve both. N5 fixed the numerator union, not these two formulas.
**Proposed correction:** In AK-ACC-05 replace "the owner's own turn usage" with "the owner's own exclusive records (all categories; delivery + overhead)". In AK-ACC-14 and `docs/09` §9 define the denominator as accepted root tasks of the cohort, with a child's acceptance counted through its root only, and add an accepted-child assertion to T-09.
**Evidence:** `spec.md` AK-ACC-05, AK-ACC-14; `docs/09` §4 (worked example), §9 (formula and cohort prose); `docs/10` T-09; `evals/fixtures/task.json` cost subtotals.
**Confidence:** high

### DEEPSEEK-7 · The closed support-level set cannot name a verified projected skill
**Severity:** minor
**Finding:** AK-SKL-04 closes a route's support level to `native-verified`, `native-unverified`, `projected-unverified`, `prompt-injected`, `unsupported`, while `docs/04` §2 says a verified `projected` (or `prompt-injected`) entry "renders as such with its evidence" and the mechanism set includes `projected`. A projected skill that passes verification therefore has no level in the closed set: `projected-unverified` misstates it, `native-verified` would claim native execution, and `unsupported`/`prompt-injected` are different mechanisms. The fixture uses `{mechanism, verified}` rather than one of the five names, so the stored schema and the normative level set are not the same contract. N8 fixed the entry shape, not the level set.
**Proposed correction:** Either add `projected-verified` to AK-SKL-04 (keeping `native-verified` the only level that satisfies a native floor) or define the support state as the pair `{mechanism, verified}` with the display label derived; align `docs/04` §2, `docs/05` §3 and `docs/15` §4.
**Evidence:** `spec.md` AK-SKL-04; `docs/04` §2 (rendered levels and verified-projected sentence); `docs/05` §3; `docs/15` §4; `evals/fixtures/skill-package.json`.
**Confidence:** high

### DEEPSEEK-8 · Silence codes are not one-to-one with AK-COL-05
**Severity:** minor
**Finding:** AK-COL-05 lists six justifying clauses and claims the §3.2 codes "form a closed set that maps one-to-one onto these clauses"; `docs/08` repeats "Every code maps to exactly one AK-COL-05 clause; the closed set here and the normative list are identical." The table has eight codes: `not_addressed` and `no_evidence` both express the "not addressed and no evidence to add" clause (the table itself tags `no_evidence` with that clause while `not_addressed` has the same meaning), and `quiet_hours` and `policy_hold` both express the sixth clause (quiet hours or explicit room rule). Two clauses have two codes each, so the mapping is many-to-one, not one-to-one, and the "identical" claim is false. M15 fixed the code set and the direct-question guard; the mapping claim remains wrong.
**Proposed correction:** Collapse to exactly one code per clause (for example, keep `no_evidence` and remove or alias `not_addressed`; keep `policy_hold` for the room rule and either fold quiet hours into it or split the sixth clause), or change the normative claim to "every code maps to exactly one clause" and document the many-to-one cases. Update the policy-table test accordingly.
**Evidence:** `spec.md` AK-COL-05; `docs/08` §3.2 table and the claim below it; round-1 consolidation M15.
**Confidence:** high

### DEEPSEEK-9 · The backup completeness gate has two incompatible definitions of "complete"
**Severity:** minor
**Finding:** AK-OPS-04 defines the complete restore set as "database, attachments, memory, artifacts, settings, skill/procedure/template registry, action and usage ledgers, and configuration". It does not name the workspace checkpoint refs/bundles that `docs/12` §5.1 item 7 and T-13 require, even though AK-OPS-16 says a generation holds "the complete restore set of AK-OPS-04 with each source tree under its own path". An implementer following the requirement's enumeration would omit item 7; one following the procedure would include it. In addition, the manifest step in `docs/12` §5.2 hashes every file with `find`, while AK-OPS-16 requires "a manifest with one checksummed entry per item" and the gate requires an absent item to be "listed as absent, with the reason, not skipped"; a per-file manifest has no entry for an empty or absent source tree and no absent marker. N1 added item 7 to the procedure but did not update AK-OPS-04 or the manifest's per-item semantics. This is distinct from CHATGPT-1's missing `$GEN/checkpoint-refs` directory: even with that directory created, the requirement's list and the manifest's per-item/absent-item semantics remain inconsistent.
**Proposed correction:** Use one seven-item list: add "workspace repositories and `refs/t3/checkpoints` refs/bundles" to AK-OPS-04 (secrets remain separately encrypted/re-entered as stated), and make the manifest one entry per item (path, checksum or `absent: reason`) with optional per-file detail. Extend T-13 to remove a whole source tree and assert the absent marker, not only a file.
**Evidence:** `spec.md` AK-OPS-04, AK-OPS-16; `docs/12` §5.1 items 1–7, §5.2 manifest step and completeness gate; `docs/10` T-13; `docs/04` `TaskCheckpoint.workspaceCheckpointRef`.
**Confidence:** high
