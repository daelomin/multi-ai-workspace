# GROK review — round 2

Reviewed `spec.md` v0.4 after `reviews/round-1/CONSOLIDATION.md`, with `decisions.md` (AKIRA-D1–D6 fixed), companion documents `docs/01`–`docs/15`, and the eight records in `evals/fixtures/`. U4–U16 stay carried forward; none is raised again. The declared `assets/` directory is absent, as round 1 already recorded, and no requirement reviewed here depends on it. This is a specification review. A read-only `rsync` dry run checked destination layout and wrote nothing into the project. No validator, git command, install, deployment, authentication, spend or live integration was run. Upstream runtime behaviour is not asserted.

Findings: four major, five minor.

### GROK-1 · The backup procedure does not produce the restore set it names
**Severity:** major
**Finding:** AK-OPS-04/05/16 and `docs/12-operations.md` §5.1 require each run to write a uniquely named generation of the whole restore set. The §5.2 procedure does not. `rsync -a "$STATE"/{attachments,artifacts,memory}/ "$GEN"/` copies the contents of three trees into one directory, so the generation no longer records which tree a file came from, and identical relative paths collide. A dry run of that trailing-slash form with `attachments/same/note.txt`, `artifacts/same/note.txt` and `memory/same/note.txt` listed a single destination path, `same/note.txt`. The same procedure never copies secrets (item 4), configuration (item 5), content-addressed template/skill/procedure files (item 6) or git checkpoint refs and objects (item 7), and it never writes the manifest it says a complete backup must have. The database snapshot is `state-$(date +%F).sqlite`, one name per calendar day, while `$GEN` is named to the second. SQLite's `VACUUM INTO` fails with an error when the destination already exists and is not an empty file, so a second run on the same day cannot create the new database generation AK-OPS-16 requires. T-13 checks that a later generation does not delete an earlier file. It does not check path identity inside a generation or the omitted items. A run that follows the procedure can satisfy the current test and still be unrestorable.
**Proposed correction:** Copy each tree to its own destination (`$GEN/attachments/`, `$GEN/artifacts/`, `$GEN/memory/`). Add checked steps for the encrypted secret set, configuration, the content-addressed registry (or its export bundle), and checkpoint refs plus objects. Name the database snapshot with the same per-run timestamp as `$GEN`. Write a manifest with one checksummed entry per §5.1 item. Extend T-13 and the T-11 restore checklist to require all seven items, and to require three distinct hashes when the same relative filename exists in all three trees.
**Evidence:** `spec.md` AK-OPS-04 (1308–1311), AK-OPS-05 (1313–1316), AK-OPS-16 (1363–1366); `docs/12-operations.md` §5.1 items 1–7 (119–131) against §5.2 (136–160); `docs/10-tests-and-acceptance.md` T-13 (214–223). SQLite documentation, §2.1, consulted 2026-10-25: the `INTO` file must not already exist, or it must be empty, otherwise `VACUUM INTO` fails with an error (`https://sqlite.org/lang_vacuum.html`). The dry run above used only `/tmp` fixtures.
**Confidence:** high

### GROK-2 · Startup reconciliation can dispatch during recovery quarantine
**Severity:** major
**Finding:** AK-OPS-15 requires a restored or rolled-back server to start with autonomous dispatch disabled, and to reconcile every task or routine that could have acted in the uncertain interval before any release. AK-TSK-14 still tells every server start, with no quarantine exception, to take queued work that was never dispatched and "dispatch or mark". T-14's fail signal is "Task dispatched on startup". Both cannot be implemented. The operator checklist that is supposed to carry AK-OPS-15 narrows the set further: `docs/12-operations.md` §5.3 step 2 lists only tasks that were `ready`, `running`, `blocked` or `awaiting_input` at the snapshot, plus routines due in the interval. `docs/04-data-model.md` §4.1 allows `paused → ready` and reopening `done`/`failed`/`cancelled`. A task in one of those states at the snapshot can send a non-idempotent message before the failure and still be outside the checklist. Work created after the snapshot is also absent from the restored database, and the checklist gives no inventory rule for it. Releasing quarantine because a task was not in those four states replays an effect the snapshot does not contain.
**Proposed correction:** State that while recovery quarantine is on, AK-TSK-14 may mark or block, and must not dispatch, start a routine, or send. Make §5.3 step 2 the same set as AK-OPS-15: every task or delivery that could have acted, whatever its snapshot status, including work present only in preserved post-snapshot evidence. Absence from the four listed states is not a release. Add a paused-at-snapshot case and a post-snapshot delivery to T-14.
**Evidence:** `spec.md` AK-TSK-14 (730–734), AK-OPS-15 (1355–1361); `docs/12-operations.md` §5.3 steps 1–4 (173–188); `docs/04-data-model.md` §4.1 (254–268); `docs/10-tests-and-acceptance.md` T-14 (225–237) and F-16 (273).
**Confidence:** high

### GROK-3 · An unresolved external action can still be followed by another send
**Severity:** major
**Finding:** AK-RTE-12 and `docs/04-data-model.md` §4.2 say a failure after an action is `dispatched` or `unknown` is `interrupted` or `failed_unknown` and is ineligible for automatic fallback until reconciliation. Three other normative texts still authorize the next send. The error taxonomy (`docs/05-interfaces.md` §6) sets `rate_limited` and `network` to retry and to infrastructure fallback, with no dispatched-action exception, and says that taxonomy is shared by attempts, UI and routing. F-02 expects a 429 to back off and then fall back; F-03 is the only fault that states the two sub-cases. The cancel edge (`docs/04-data-model.md` §4.1) lets the canceller move `running` to `ready` with no requirement to reconcile `dispatched`/`unknown` actions first, while the `failed_unknown`/`interrupted` edge on the next row has that guard. Invariant 4 blocks dependent actions, not a new attempt of the same task. A new attempt can issue the same logical intent; AK-TSK-13 scopes the idempotency key to that intent, which does not establish that the first call failed. Separately, the taxonomy names (`auth_expired`, `quota_exhausted`, `tool_contract`, `rate_limited`) are not members of `AttemptOutcomeClass`, and F-01, F-04 and F-05 grade those names as the expected outcome. AK-TSK-14 says to mark a dead running attempt "failed"; §4.2 names that outcome `interrupted`. An implementer cannot satisfy the closed outcome set, the fault matrix and the no-replay rule together.
**Proposed correction:** Add one table from every taxonomy class to one `AttemptOutcomeClass`, including `auth_missing` and `entitlement`. In that table and in F-02, allow retry or infrastructure fallback only when no action is `dispatched` or `unknown`; otherwise the outcome is `interrupted` or `failed_unknown`. Give the cancel edge, and any later `task.start`, the same reconciliation guard the interrupted edge already has. Use `interrupted` in AK-TSK-14. Add the 429-after-send case and the cancel-with-unknown-action case to the fault matrix.
**Evidence:** `spec.md` AK-RTE-12 (495–503), AK-TSK-11 (713–716), AK-TSK-13 (724–726), AK-TSK-14 (730–734); `docs/04-data-model.md` §4.1 (258–263), §4.2 (274–289), invariant 4 (440); `docs/05-interfaces.md` §6 (215–232); `docs/10-tests-and-acceptance.md` F-01 through F-05 (258–262).
**Confidence:** high

### GROK-4 · "Specification-led" is a dispatch guard with no decision procedure
**Severity:** major
**Finding:** AK-TRG-07 and the `triaged → ready` guard block a `not-ready` task from a "specification-led" route, and allow an "advanced" route that meets the capability floor. `meetsFloor` is defined. "Specification-led" and "advanced" are not. `RouteDecision` and its candidates record `meetsFloor`, `available`, cost and skill support, and no field or rule that splits two floor-meeting routes into specification-led and advanced. The same guard also says the route must meet the floor, so a below-floor route is already rejected for every readiness outcome. T-10 still requires the cheap-build path to stay disabled while a floor-meeting advanced route proceeds. An implementer cannot tell which floor-meeting route the `not-ready` result forbids.
**Proposed correction:** Define the predicate in one place: either a route-policy flag (`role: specification-led | advanced`) stored on the candidate and evaluated by the guard, or an explicit rule such as "the lowest-cost floor-meeting route is specification-led; any other floor-meeting route is advanced". State that `not-ready` rejects only the flagged routes, and that below-floor remains rejected by the floor check alone. Put the flag in the route-decision fixture and in T-10.
**Evidence:** `spec.md` AK-TRG-06 (586–592), AK-TRG-07 (594–597), AK-TSK-01 (663–664); `docs/04-data-model.md` §3 `RouteDecision` (208–222), §4.1 (249), §4.3 (314–315); `docs/10-tests-and-acceptance.md` T-10 (172–175). Round-1 M8 aligned the wording of the guard and removed "assessment override"; it did not define the predicate the guard now uses.
**Confidence:** high

### GROK-5 · CPAT sums overlapping inclusive totals
**Severity:** minor
**Finding:** `docs/09-accounting.md` §9 defines the cost-per-accepted-task numerator as the sum of inclusive costs of all tasks of a class. Inclusive cost already contains descendant tasks. A parent and a child of the same class are both added, so the child's cost is counted twice. Parent exclusive $1 and child exclusive $1 become inclusive totals $2 and $1; the formula yields $3 for $2 of records. The distinct-task denominator does not correct that. The function is also `CPAT(route, taskClass)`, and the text never says which route receives a task that switched routes. AK-ACC-14 defines that metric, AK-TRG-14 makes it the headline optimisation figure, and AK-ACC-16 feeds it to routing calibration. §4 check 2 already forbids summing a parent inclusive total together with its child for a team roll-up.
**Proposed correction:** Compute the numerator from the union of effective usage-record ids for an explicit cohort (root tasks only, or all tasks, stated once), counting each record once. Attribute a multi-route task by a stated rule (chosen route, attempt that delivered, or split by attempt). Use the same cohort in the denominator. Add a same-class parent/child example to T-09.
**Evidence:** `docs/09-accounting.md` §4 checks 2 and 6 (156–168), §9 (247–268); `spec.md` AK-ACC-05 (1018–1022), AK-ACC-14 (1057–1062), AK-ACC-16 (1067–1069), AK-TRG-14 (632–635).
**Confidence:** high

### GROK-6 · A checkpoint cannot see the task-definition change it must report
**Severity:** minor
**Finding:** AK-TSK-06 and AK-TSK-14 require a task-definition revision in the checkpoint and require resume to surface a mismatch rather than guess. `Task` has no revision or content hash. `TaskCheckpoint.taskRevision` is `{title, acceptanceCriteria, triageRevision}`. In `evals/fixtures/checkpoint.json`, `acceptanceCriteria` is a list of ids. A change to a criterion's statement or validation, to the assignee, or to dependencies leaves that tuple equal. Resume then reports no mismatch and continues against a different task definition.
**Proposed correction:** Give `Task` a monotonic revision and a content hash covering the fields that define the work. Store `{taskId, revision, contentHash}` in the checkpoint. Compare them before dispatch and surface a mismatch. Add the changed-criterion case to T-02 or T-14.
**Evidence:** `spec.md` AK-TSK-06 (685–689), AK-TSK-09 (701–703), AK-TSK-14 (730–734); `docs/04-data-model.md` §3 `Task` (167–180) and `TaskCheckpoint` (224–227); `evals/fixtures/checkpoint.json` `taskRevision`.
**Confidence:** high

### GROK-7 · `Money` is undefined and the cost fixtures use another shape
**Severity:** minor
**Finding:** `docs/04-data-model.md` §1 says money is minor units plus currency. `UsageRecord.cost` follows that (`amountMinor`, `currency`), and `usage-record.json` stores `"amountMinor": 184`. `CostSummary` then uses an undefined type `Money` for provenance subtotals, and `combinedEstimate` is `{amount: Money; currency: string}`, which repeats currency if `Money` already contains it. `task.json` stores decimal numbers (`0.82`, `3.12`) in those fields and omits `byCategory`, which §5 requires on `CostSummary`. The golden records cannot validate against the published summary type.
**Proposed correction:** Define `Money` once as `{amountMinor: integer; currency: string}` and use it for usage cost, subtotals and `combinedEstimate` (one currency field). Regenerate the task-fixture amounts in minor units and include `byCategory`, or mark `byCategory` optional in a summary response and say so. Point the fixture check in `docs/10-tests-and-acceptance.md` §4 at that definition.
**Evidence:** `docs/04-data-model.md` §1 (20–21), §5 `UsageRecord.cost` (369–370), `CostSummary` (379–386); `evals/fixtures/task.json` (62–81); `evals/fixtures/usage-record.json` cost object; `docs/10-tests-and-acceptance.md` §4 (290–294).
**Confidence:** high

### GROK-8 · Per-route skill verification does not fit the skill record
**Severity:** minor
**Finding:** AK-SKL-04 and `docs/05-interfaces.md` §3 require every per-route entry to carry a mechanism and a separate `verified` flag, including `prompt-injected`. `SkillPackage.support` is still a single enum per route, with verified/unverified split only for `native`, and a bare `prompt-injected` value. `supportEvidence` requires `verifiedAt`, `model` and `evidence` on every entry. The unverified DeepSeek entry in `evals/fixtures/skill-package.json` has none of those fields; it has `verified: false` and a `note`, which the type does not declare. An unverified route cannot be recorded without inventing a verification timestamp, and a verified prompt-injected route has no enum value.
**Proposed correction:** Define one support entry: route key, mechanism (`native` | `projected` | `prompt-injected` | `unsupported`), and `verified`. Require `verifiedAt`, `model` and `evidence` only when `verified` is true. Align the fixture. Keep the executable validator as implementation work, and require it to reject an evidence object that does not match that rule.
**Evidence:** `spec.md` AK-SKL-04 (775–781); `docs/05-interfaces.md` §3 (160–167); `docs/04-data-model.md` §2 `SkillPackage.support` and `supportEvidence` (135–137); `evals/fixtures/skill-package.json` (31–42).
**Confidence:** high

### GROK-9 · Unauthorized action has no incident procedure
**Severity:** minor
**Finding:** AK-OPS-08 requires a documented recovery for an unauthorized action, together with nine other incident classes. `docs/12-operations.md` §7.1–§7.9 cover provider outage, credit exhaustion, credential revocation, database corruption, duplicate or lost external action, secret exposure, runaway spend, disk full and deletion accident. There is no procedure for a bot or actor acting outside its grant, or for an external write the policy did not allow. Containment, evidence preservation and revocation are unspecified for that class.
**Proposed correction:** Add a runbook: stop dispatch for the affected bot or connector (kill switch when the scope is unclear), keep the event, action and audit records and the artifact hashes, revoke the credential or grant, reconcile any `dispatched`/`unknown` effect before restart, notify the operator, and record the incident. Add that runbook to the release-gate list in `docs/10-tests-and-acceptance.md` §7.
**Evidence:** `spec.md` AK-OPS-08 (1327–1329); `docs/12-operations.md` §7.1–§7.9 (228–279); `docs/10-tests-and-acceptance.md` §7 (357–366).
**Confidence:** high
