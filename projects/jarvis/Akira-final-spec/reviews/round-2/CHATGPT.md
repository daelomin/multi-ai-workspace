Reviewed `spec.md` v0.4 after the round-1 reviews and `CONSOLIDATION.md`, with `decisions.md`, all fifteen companion documents and all eight JSON fixtures in the manifest scope. AKIRA-D1–D6 remain fixed; U4–U16 are carried forward without new decision requests. The declared `assets/` directory is absent, as already recorded in round 1. Findings: one major, three minor.

### CHATGPT-1 · The backup command loses the source directory hierarchy
**Severity:** major
**Finding:** `docs/12-operations.md` §5.2 now preserves generations, but `rsync -a "$STATE"/{attachments,artifacts,memory}/ "$GEN"/` copies the contents of all three directories into the same destination root. The backup therefore loses whether a file belonged to attachments, artifacts or memory. Equal relative filenames from different source trees collide, leaving only one destination path for distinct source files. A fresh generation prevents deletion of old generations but does not make this generation a faithful restore set. This violates AK-OPS-04/05 and can leave recovery without the original files. This is a remaining defect in the runbook amended by M1, not a repetition of the resolved deletion-flag finding.
**Proposed correction:** Preserve each source directory under the generation, for example by copying the three directory paths without their trailing slashes into `$GEN/`, or using explicit `$GEN/attachments/`, `$GEN/artifacts/` and `$GEN/memory/` destinations. Extend T-13 or the restore drill with distinct contents at the same relative filename in all three trees; require all three restored paths and hashes to match.
**Evidence:** `docs/12-operations.md` §5.1 requires the separate file trees; §5.2 supplies the merging command. A read-only `rsync -ani` using the existing `docs/` and `evals/fixtures/` directories with the same trailing-slash pattern listed their files together at the destination root, without either source directory name. T-13 currently checks preservation between generations, not path preservation within a generation.
**Confidence:** high

### CHATGPT-2 · Summing inclusive task costs double counts same-class descendants in CPAT
**Severity:** minor
**Finding:** `docs/09-accounting.md` §9 now defines the CPAT numerator as the sum of inclusive attributable costs of all tasks of a class. If a parent and its child have that same class, the child's cost enters through both the parent's inclusive total and the child's own inclusive total. For example, parent exclusive $1 and child exclusive $1 produce inclusive totals $2 and $1: the formula counts $3 although only $2 was consumed. The distinct-accepted-task denominator fix does not fix this numerator. The displayed function also takes a route argument without defining how a task that used multiple routes is assigned to that route's cohort.
**Proposed correction:** Define the task cohort explicitly and compute its numerator from the union of effective usage-record ids, counting each record once, rather than summing overlapping inclusive totals. State whether accepted units are root deliveries or include child tasks, and use that same cohort in the denominator. Define route attribution for switched tasks before using this metric for calibration. Add a same-class parent/child example and a multi-route example to T-09.
**Evidence:** `docs/09-accounting.md` §9 explicitly sums inclusive costs of all tasks of the class; §4 double-counting check 2 already warns against summing overlapping parent and child totals for team reporting. AK-ACC-05/14/16 and AK-TRG-14 require nonduplicated costs for routing calibration. Round-1 M9 corrected rework and overhead arithmetic, but the revised cohort formula still permits this descendant overlap.
**Confidence:** high

### CHATGPT-3 · Recovery checklist enumerates fewer cases than the quarantine requirement
**Severity:** minor
**Finding:** AK-OPS-15 correctly requires reconciliation of all tasks that could have acted during the recovery interval. The corresponding operational checklist in `docs/12-operations.md` §5.3 step 2 enumerates only tasks that were `ready`, `running`, `blocked` or `awaiting_input` at the snapshot. A task paused at the snapshot can resume, send and confirm a non-idempotent message before failure; a terminal task can likewise be reopened. Both are outside that checklist despite being covered by the normative rule. Tasks and channel deliveries created after the snapshot also require an explicit inventory strategy when their local records have been lost. This is an alignment gap in M3's runbook, not an objection to recovery quarantine itself.
**Proposed correction:** Make the checklist cover every task or delivery that could have acted, irrespective of snapshot status or presence. Use preserved evidence to narrow that set; otherwise keep potentially affected work quarantined. Include a paused-at-snapshot task that resumed and acted, plus post-snapshot work absent from the restored database, in the recovery drill. State that a task's absence from the enumerated snapshot states is not sufficient for release.
**Evidence:** AK-OPS-15 uses the broader “could have acted” rule; `docs/12-operations.md` §5.3 step 2 lists four snapshot states. `docs/04-data-model.md` §4.1 explicitly permits `paused → ready` and terminal-state reopening. T-14/F-16 currently exercise a task that was `ready` at the snapshot only.
**Confidence:** high

### CHATGPT-4 · Revised fixture contracts still disagree with their canonical shapes
**Severity:** minor
**Finding:** The schema-version and arithmetic corrections are present, but the examples still cannot all satisfy the published shapes. `docs/04-data-model.md` §5 requires `CostSummary.byCategory`; all three cost summaries in `task.json` omit it. The skill schema in §2 requires `verifiedAt`, `model` and `evidence` on every `supportEvidence` entry, while the new unverified DeepSeek entry in `skill-package.json` has none of them. The separate per-route `verified` flag required by AK-SKL-04 and `docs/05` §3 is also not represented in the canonical support-entry type. An unverified entry should not need a fabricated successful-verification timestamp or evidence. These are remaining contract mismatches after M12/M13, rather than a request to implement the deferred validator during this review.
**Proposed correction:** Publish a support-entry shape with mechanism and verification state, requiring successful-verification fields only when verified. Align the fixture with that shape. Either populate `byCategory` in each cost summary or explicitly make it optional in summary responses. Keep the planned executable validator as implementation work and require it to reject these mismatches once the shapes are fixed.
**Evidence:** `docs/04-data-model.md` §2 `SkillPackage.support/supportEvidence` and §5 `CostSummary`; `docs/05-interfaces.md` §3 orthogonal-verification rule; `evals/fixtures/skill-package.json` DeepSeek evidence entry; `evals/fixtures/task.json` exclusive/inclusive/overhead summaries. Read-only field checks confirmed the omitted fields. `docs/10-tests-and-acceptance.md` §4 and `docs/04` §9 describe these as schema-test/golden records.
**Confidence:** high
