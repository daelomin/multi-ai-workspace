### GROK-1 · AFIR live status is a recharging point, and the spec treats it as a connector

- **Section:** §3.2, §4.3, §14
- **Type:** error
- **Severity:** major
- **Finding:** §14 says AFIR gives connector-level operational status in Europe. Commission Implementing Regulation (EU) 2025/655, Annex Table F, sets both operational status and availability at data level **Point**. Table B defines the recharging-point ID, then a separate "Number of connectors" field: a recharging point may have one or more connectors, and only one can be used at a time. Copying that point status onto a `connector` subject will mark the wrong plug, or every plug on the point, as in use or non-operational. The §3.2 subject enum has no recharging point, so the record the spec says to ingest cannot be stored without overloading `connector` or `evse`. The same article says the regulation is binding in all Member States. The closing "in Europe" sentence is wider than that: it does not cover the UK or Switzerland. Which source covers those countries is already an open question in `decisions.md`; this finding does not choose one. Table F's "non-operational" means a technical problem or maintenance. It is operator-reported point status, not a ground fault, a fire, or an internal diagnostic.
- **Proposed change:** Replace the §14 AFIR closing sentence with: "Implementing Regulation (EU) 2025/655 gives recharging-point operational status and availability through EU Member State national access points. A recharging point may have more than one connector. Store the point as its own subject; do not copy point status onto each connector as an independent observation, and do not assume the point is an OCPP connector or EVSE. Operational status is `operational` or `non-operational`. Availability is `in use`, `reserved` or `not in use`. Record them as `station_status` observations with those literals, a field path that keeps the two data types apart, and `source_type` `regulator`. They are not `protocol_error` observations and they do not by themselves raise a hazard or a restriction. An AFIR connector-type value of Megawatt Charging System stays `unsupported_scope`. The regulation does not cover the UK or Switzerland." Add `recharging_point` to the §3.2 `subject_type` enum, used for this subject. Keep the existing limit that NAP data is not internal diagnostics.
- **Evidence:** [Commission Implementing Regulation (EU) 2025/655](https://eur-lex.europa.eu/eli/reg_impl/2025/655/oj/eng), Annex Table B (recharging point ID; number of connectors; connector type, including Megawatt Charging System) and Table F (operational status and availability at level Point), and the closing provisions (applies from 14 April 2025; binding and directly applicable in all Member States; done at Brussels, 2 April 2025), checked 2026-10-21.
- **Confidence:** high

### GROK-2 · The DIN 70121 row is an ISO row, and basic AC still leaves `safety_checks` unmarked

- **Section:** §3.3, §12
- **Type:** error
- **Severity:** minor
- **Finding:** The coarse ISO 15118-2 order in v0.4 is right. The shared `iso15118`, `din70121` row is not. A published description of DIN SPEC 70121 limits it to DC, allows only ExternalPayment, and uses an empty ContractAuthentication rather than a contract certificate. Cable check and precharge are in that DC sequence, so the row's "DC only" bracket would let an implementer mark them `not_applicable` on a DIN session. The same gap remains on AC: `safety_checks` is in the closed stage list, and neither the PWM-only row nor the AC reading of the ISO row marks it `not_applicable`. The §12 fixture checks `communication_setup` and `parameter_negotiation` only, while §3.3 also marks protocol `authorization` `not_applicable` on PWM-only AC. Separately, a vendor application note now gives a CHAdeMO stage order the spec still leaves unspecified. That note is not the CHAdeMO text.
- **Proposed change:** Split the profile row. For `iso15118`, keep authorization after communication setup and before parameter negotiation; `safety_checks` (cable check, then precharge) apply on DC only and are `not_applicable` on AC. For `din70121`, use that same DC order with `safety_checks` always applicable, and state that the profile is DC-only and that `plug_and_charge` is not an allowed `authorization_method` (external payment only). For `iec61851_pwm_only`, add `safety_checks` to the stages marked `not_applicable`. For `chademo`, set: discovery → connected → communication_setup → parameter_negotiation → safety_checks (insulation test before the vehicle battery is connected) → power_delivery → charging → stopping. Protocol `authorization` is `not_applicable`; external identification stays an `external_authorization` event. Do not reuse ISO 15118 message names, and label this CHAdeMO order as taken from a vendor application note pending the CHAdeMO text. Extend the §12 stage fixture so a PWM-only session marks `communication_setup`, `authorization`, `parameter_negotiation` and `safety_checks` as `not_applicable`.
- **Evidence:** [Typhoon HIL, DIN 70121](https://typhoon-hil.com/documentation/typhoon-hil-software-manual/References/din70121_protocol.html), checked 2026-10-21: DC only, no Plug & Charge, ExternalPayment only, then ChargeParameterDiscovery, CableCheck, PreCharge, PowerDelivery. [Siemens, TIA library for CHAdeMO specification V0.9.1 to V2.0](https://cache.industry.siemens.com/dl/files/961/109779961/att_1052261/v1/FB_CHAdeMO_en-US_20210118AB.pdf), section 3.4, checked 2026-10-21: CAN start, parameter exchange, insulation test, battery connection, charging, termination with welding detection. Both are secondary descriptions, not the DIN or CHAdeMO texts. The PWM and fixture points are reasoning only against §3.3 and §12.
- **Confidence:** high on DIN being DC-only and without Plug & Charge; medium on the CHAdeMO order, because the source is a vendor library note.

### GROK-3 · `measurement_location` is who reported the value, and `measurement_kind` is the quantity

- **Section:** §3.2, §6.4
- **Type:** inconsistency
- **Severity:** minor
- **Finding:** The location enum is `vehicle_reported`, `charger_reported`, `meter`, `unknown`: the reporter. The kind example also uses "charger-side power versus vehicle-side power", and §6.4 forbids comparing "charger output" with "battery-reported power". Those phrases mix the physical quantity with the reporter. A vehicle can report charger output, and a charger can report battery input. Collapsing charger-versus-vehicle into `measurement_location` would make those two readings of one quantity incomparable, and would leave charger output and battery input as the same kind. The merged measurement rule still needs both axes, with kind carrying the quantity.
- **Proposed change:** In §3.2, define `measurement_kind` as the physical quantity and `measurement_location` as the reporter. State that the kind catalog distinguishes charger output power, battery input power, and energy, and that a comparison requires the same kind. Replace the kind example "charger-side power versus vehicle-side power" with "charger output power versus battery input power". In §6.4, replace "battery-reported power" with "battery input power". A vehicle report of charger output and a meter reading of charger output are the same kind and may be compared only under the catalog's rule for differing reporters.
- **Evidence:** reasoning only; local §3.2 enum and kind example against §6.4. This corrects the axis left open by round-2 D1. It disagrees with treating the charger-versus-vehicle split as a location.
- **Confidence:** high
