### DEEPSEEK-1 · An inter-stage element's power cap has no defined terminal voltage on a two-stage path

- **Section:** §7.2 (Per-element power caps around a converter; Converter stages), §9
- **Type:** gap
- **Severity:** major
- **Finding:** The per-element paragraph gives `V_e` only for elements downstream of the final converter (`V_e = V_batt + I_batt * R_batt_to_e`) and for elements upstream of stage 1 (`V_e = V_in + I_in_used * R_in_to_e`). For an element between stage k and stage k+1 it says only "at the voltage along that segment"; it never states which terminal of the element is used or gives a formula. The only fallback bound the paragraph names is "(`V_station` upstream, `V_out` downstream)", and a middle segment is upstream of the final converter but not upstream of stage 1, so the text invites `V_station` for it. In the round-5 400/600/800 V case, with 40 kW at an 800 V battery and 0.9 per stage, the inter-stage current is 74.07 A and a 40 kW inter-stage cable carries 600 V × 74.07 A = 44.44 kW, so the cable must fail; evaluating it at `V_station` = 400 V gives 29.63 kW and passes it. The first sentence ("checked against its own ... power cap at its own terminal voltage, on its own side of the converter") states the principle but is single-stage wording, and the §9 round-5 two-stage regressions check only the segment *current*, never a middle-segment power cap. The safety rule is therefore not implementable deterministically for the two-stage path that J1/J2 added.
- **Proposed change:** Add after the station-side formula: "For an element in the segment between stage k and stage k+1, `V_e = V_out_k - I_out_k * R_outk_to_e`, where `R_outk_to_e` sums the resistances allocated between stage k's output and e's station-side terminal (stage k's output resistance included when its declared location lies in that interval), and the check is `V_e * I_out_k / 1000`. When only that segment's total resistance is known, every element of it is evaluated at `V_out_k`, recorded in `assumptions`." In the fallback parenthetical, name the final stage's voltage (`V_out_N`) and state that `V_station` is the bound only for the segment upstream of stage 1. Also make the station-side interval explicit: `R_in_to_e` runs from the converter input to e's station-side terminal, so it does not cross e's own resistance. Add a §9 regression: the 400/600/800 V two-stage case with a 40 kW inter-stage cable cap is ineligible at 44.44 kW, and evaluating that cable at `V_station` does not pass it.
- **Evidence:** reasoning only; `40 / 0.9 = 44.44 kW`, `44.44 kW / 600 V = 74.07 A`, `600 V * 74.07 A / 1000 = 44.44 kW`, `400 V * 74.07 A / 1000 = 29.63 kW`. The values are the spec's own round-5 regression voltages and current. J2 merged the segment-current rule but the merged paragraph still has no middle-segment voltage rule.
- **Confidence:** high

### DEEPSEEK-2 · "0.81 from stage 2 input to stage 1 input" is one stage off

- **Section:** §7.2 (Converter stages), §9
- **Type:** error
- **Severity:** minor
- **Finding:** The sentence "With no inter-stage loss, efficiencies multiply (0.9 and 0.9 give 0.81 from stage 2 input to stage 1 input)" reverses the stage at which the second efficiency applies. From stage 2's input to stage 1's input only stage 1's efficiency is crossed: `P_in_1 = P_in_2 / 0.9`, a factor of 1.111, not 0.81. The 0.81 product correctly runs from stage 1's input to stage 2's output (the battery side), that is `P_in_1 = P_out_2 / (0.9 * 0.9)`. With 40 kW at the battery and zero resistance the correct stage-1 input is `40 / 0.81 = 49.38 kW`; following the parenthetical literally gives `P_in_2 / 0.81 = 44.44 / 0.81 = 54.87 kW`, 11% higher, and it contradicts the §9 round-4 regression's 50.49 kW bound, which divides the inter-stage loss by only the upstream efficiency. This is the qualification J4 added to the "efficiencies multiply" sentence.
- **Proposed change:** Replace the parenthetical with: "With no inter-stage loss, efficiencies multiply from stage 1's input to stage N's output (`0.9 * 0.9 = 0.81`, so `P_in_1 = P_out_N / 0.81`); between stage 2's input and stage 1's input only stage 1's efficiency applies (`P_in_1 = P_in_2 / 0.9`)." Keep the following clause about the inter-stage `I^2 * R_mid` loss, which is correct.
- **Evidence:** reasoning only; `40 / 0.9 = 44.44 kW`, `44.44 / 0.9 = 49.38 kW`, `44.44 / 0.81 = 54.87 kW`, and the §9 round-4 regression `(40 / 0.9 + 1) / 0.9 ≈ 50.49 kW`.
- **Confidence:** high

### DEEPSEEK-3 · A partial AC request leaves the request/outlet precedence contradictory

- **Section:** §7.2 (AC inputs), §8.2, §9
- **Type:** inconsistency
- **Severity:** minor
- **Finding:** The paragraph gives per-value precedence ("When both a request value and an outlet value are present, the request value is used") and then forbids mixing: "the two sources are never mixed field by field (a request voltage is not combined with an outlet convention)". If the request supplies `ac_supply_voltage_v` but not `ac_voltage_convention` or `power_factor` (both optional in §8.2), the first rule takes the convention and power factor from the outlet — precisely "a request voltage combined with an outlet convention" — while the second rule forbids it. "If any is absent, AC power is `unknown`" does not resolve the case, because no value is absent across both sources. The §9 regression ("AC request 230 V with an outlet declared 400 V line-to-line ... no field is mixed between the two") names no request convention or power factor, so it does not state whether the result is a computed AC power or `unknown`. The AC result, and any AC candidate's eligibility, therefore still depends on which sentence is read first. This is the merged J14 text; the partial-request case was not the case round 5 settled.
- **Proposed change:** State the precedence for a partial request explicitly, for example: "The voltage and the convention that interprets it must come from the same source. If the request supplies a voltage, the convention must also come from the request; a missing request convention makes AC power `unknown`, never the request voltage with the outlet convention. The power factor is taken from the request when present, otherwise from the outlet. The source of each value used is recorded in `assumptions`." Then state in the §9 regression whether the request carries its own convention and power factor, or that the result is `unknown`.
- **Evidence:** reasoning only; the quoted sentences, §8.2's nullable `ac_supply_voltage_v`/`ac_voltage_convention`/`power_factor`, and the §9 AC precedence regression.
- **Confidence:** high

### DEEPSEEK-4 · A bypassed booster's effect on series resistance is unspecified

- **Section:** §7.1 (Booster engagement), §6.1, §7.2, §9
- **Type:** gap
- **Severity:** minor
- **Finding:** §7.1 says "A bypassed booster contributes no input limit or efficiency and the direct path (or the adapter path alone) applies", but it does not say whether the booster contributes resistance. §7.2 builds `R_series_ohm` from the `resistance_ohm` of the in-path series elements and makes an unknown in-path resistance `unknown`; `dc_booster_ratings` now stores input and output resistance (J15), and nothing says those boost-path resistances, or a bypass-path resistance, are excluded when the booster is bypassed. The §9 round-4 regression ("profile says the booster is bypassed inside the pack window: eligible on the direct path") requires eligibility, so the intended reading is that a bypassed booster adds no resistance; that is not stated, and an implementation that includes the stored side resistances, or flags them as unknown, will reject or unverify the same combination. The outcome can change whenever the path is near a boundary (the 400 V station / 400 V battery / positive-resistance case in §9).
- **Proposed change:** Add to §7.1: "A bypassed booster contributes no input limit, no efficiency and no series resistance: its `dc_booster_ratings` resistances describe the boost path and are not part of `R_series_ohm` when it is bypassed. A bypass-path resistance, when the source states one, is stored and used; otherwise the bypass is treated as a zero-ohm connection and that assumption is recorded in `assumptions`." Add a §9 regression: a bypassed booster with stored side resistances leaves the direct path eligible, not `unknown`.
- **Evidence:** reasoning only; the §7.1 sentence, §6.1's `dc_booster_ratings` resistance list, §7.2's `R_series_ohm`/unknown-resistance rule, and the §9 round-4 bypass regression.
- **Confidence:** medium

### DEEPSEEK-5 · The §5 accessory conflict list names peak current but not peak power

- **Section:** §5, §6.3, §7.2
- **Type:** gap
- **Severity:** minor
- **Finding:** The closed list that makes an accessory ineligible reads "continuous or peak current, continuous or advertised power, peak duration, `peak_mode`, ...". `peak_power_kw` and the per-side `input_power_peak_kw`/`output_power_peak_kw` are stored, enforced in §7.2 and governed by the peak budget, but the list names peak only for current and names "continuous or advertised" power — `advertised_power_kw` is a distinct column in §6.3. Two retained sources giving 60 kW and 80 kW peak power therefore do not trigger the ineligibility rule by that list, although §7.1's generic "unresolved source conflicts (§5)" is ambiguous about whether it reaches a field the list omits. This is the same closed-list pattern J7 extended for vehicle and charger fields.
- **Proposed change:** Replace "continuous or advertised power" with "continuous, peak or advertised power (including each side's continuous and peak power cap of a `voltage_conversion` adapter)", and add a §9 regression: two retained sources with different peak powers for one accessory give `unverified`, no ranked category.
- **Evidence:** reasoning only; §5's list, §6.3's `peak_power_kw`/`input_power_peak_kw`/`output_power_peak_kw`/`advertised_power_kw`, and §7.2's "continuous or peak power cap" checks.
- **Confidence:** medium
